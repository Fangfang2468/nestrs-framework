# 性能与内存

本页数值对应各节注明的历史快照。2026-10-03 后续将 scope 创建改为异步、按独立配置
完成初始化，并移除独立 `warm_up` API；该调整没有重新测量下列基准，不能把历史
延迟、内存或同机容量结果当作当前创建路径的复测。现行行为见
[core 初始化说明](../nestrs-core/README.md#6-生命周期与预热)。

本文集中保留有源码基线和原始样本的测量，以及后续修复的内存复核。数字描述各自
记录的版本与负载，不代表此后每个版本的重新测量；不同轮次不能相加作为当前容器
的加速比例。
运行期设计见 [core README](../nestrs-core/README.md)，测量脚本各有独立使用说明。
功能缺陷的触发条件、每次修复与复核过程统一见[修复记录](NESTRS_FIXES.md)；本页保留
与内存和性能有关的原始对照、口径与限制。

当前实现仍使用直接构造输入、ahash、紧凑订阅存储、复用关闭工作空间和静态地址
恢复器。下列测量按各自当时的快照解释；后续编译器修复通过功能回归，不会自动更新
这些样本，也不构成新一轮性能或部署验收。

## 1. 直接构造输入：2026-10-02

本轮将逐参数 Preparer/PreparedInput 装箱改为完整 `ConstructionInputs` 与生成 adapter
的 typed take。普通投影写入栈槽，factory 保留真实 lease frame。执行协议同步升级
为 `__nestrs_reflect_v2`，审阅 JSON 仍为独立的格式 version 1。首次计划装配、实例、
任务、factory future 和 lazy 状态仍可能分配；实现不等于整个 DI 零分配。

### 基线与方法

- before 是修改开始时的实际工作区快照，含当时未提交文件；不是 Git HEAD。
  676 个文件的 hash、快照和保护文件核对保存在 `target/direct-input-20261002/`。
- 两版分别使用匹配的 CLI、driver、bridge、core，业务源码相同，registry 依赖锁定；
  不交叉混用 v1/v2 组件。
- Linux x86_64 / WSL2，rustc 1.98.0（完整 pin 见工具链指南），current-thread Tokio，
  CPU 2，Release opt-level 3、16 codegen units、无 LTO，无 native CPU 优化。
- 22 场景 × 2 版本 × 20 轮，共 880 个独立进程；每进程 64 批、每批 32 次查询，
  合计 1,802,240 次计量查询。新旧交替运行，不删样本。
- 每批显式关闭 scope 并记录存活检查点；每个进程结束时检查被查询服务的 Probe
  构造数、Drop 数和业务 checksum。计量窗口包含公开查询与消费者实际构造，不包含
  scope 创建/关闭、procfs 读取或结果格式化。
- concrete/trait/optional 输入指向预热后的 Singleton `Base`，lazy 输入指向 Singleton
  `LazyBase`。lazy 访问场景先预热目标，测量的是新消费者句柄的首次 `get`，不是目标
  服务冷启动；Probe 统计被查询服务，不计 `Base` / `LazyBase` 自身。

指标必须区分：**累计请求字节**是分配流量；**存活请求字节峰值**是尚未释放请求的
大小总和；**RSS/VmHWM**是进程驻留页。前两者不含分配器头、块大小取整、栈和代码。
全局计数 allocator 在启动时自测 alloc/alloc_zeroed/realloc/dealloc；计时带有计数
开销，不能据此宣称生产吞吐提升。完整定义见[测量工具](../tools/bench-direct-input/README.md)。

393,216 次查询。正式样本与长循环共 886 个进程、2,195,456 次查询、57,088 个关闭

稳定下降。单机、单线程 runtime、无真实 I/O 的结果不能外推到 Windows 或并发服务吞吐。

功能回归在同轮验证了两版公开 API 行为、生命周期、取消、失败、factory 跨 await
借用、lazy、跨 crate、诊断、rustdoc 和生成代码卫生。最终验证还包含新旧 ABI 混用
拒绝。具体测试职责以 [core 测试](../nestrs-core/tests/README.md)和
[工具 fixture](../cargo-nestrs/tests/fixtures/README.md)为准，不保留会随开发过时的总用例数。

Hash/Eq 语义；排序和队列结构不变。当前实现仍使用 ahash，但随后输入协议已经变更，
下面的数字只对应原始 before/after，不能作为 v2 完整实现的新测量。

基线是当轮实际工作区的 555 文件快照，归档 SHA-256 为

## 3. 2 GiB／两核与 PostgreSQL、Redis 同机：2026-10-02

该次测量在修复 Class 绑定卫生、raw identifier、查询根收集和自定义 Cargo 根文件名后，
重新构建完整工具链并通过编译器、DI、跨 crate、文档及原版 rust-analyzer 回归，
再进行受限资源测量。修复前后的 37 个 core 生产源码文件逐一 hash 相同；下面的
并发测量使用当时完整工具链重新编译的 Release 应用。这是该次快照的运行证据，
不是后续每次查询根修复后的重新测量。

### 测量范围

- Linux x86_64／WSL2，固定 rustc 1.98.0；Release opt-level 3、无 LTO，两个 Tokio
  worker，默认 32 个激活名额。cgroup v2 将进程限制在 CPU 2、4，合计两个 CPU 配额，
  禁止 swap。编译在资源组外完成，测量的是已构建应用的运行占用。
- 框架阶段：单进程上限 512 MiB；七种负载各运行三个独立进程，每进程三波预热、
  32 波计量。每波创建一组 scope，全部完成查询后用 barrier 同时持有实例，记录
  检查点，然后逐个显式等待关闭。每波核对 checksum、构造和 Drop 数。
- 同机阶段：临时 PostgreSQL 18.4、Redis 8.6.3 和应用共享 1536 MiB／两核父组，
  为 2 GiB 部署预留约 512 MiB 系统空间。子上限分别为 PostgreSQL 640 MiB、Redis
  256 MiB、应用 512 MiB。使用独立数据库卷，不开放宿主端口；测量完成后删除本次资源。
- PostgreSQL 使用 shared_buffers=128MB、max_connections=20、work_mem=4MB、
  maintenance_work_mem=32MB。pgbench scale=10、8 个客户端、2 个线程，执行 60 秒。
  Redis 预置 50,000 个不同 key，每个 value 为 1024 B，持续执行 GET／SET；
  maxmemory=128mb、allkeys-lru，关闭 RDB／AOF。两种数据库负载与应用同时运行。

存活堆使用计数 System allocator，记录请求字节，`realloc` 以一次原子差值更新
存活量；采样预热后使用栈缓冲读取 procfs，不构造临时 JSON 对象。它仍不包含分配器
头、碎片、栈或代码。RSS 是进程驻留页；**cgroup 内存还包含被计入该组的文件缓存、
内核内存及组内基准客户端**，不能把三种口径混为一谈。

### 框架与业务数据占用

下表取各场景三次独立运行中的最大值。前五行每个 scope 查询 16 次；payload 行
每个 scope 查询一次，并实际填充 1 MiB 数据。表内不把计数器、调度和关闭耗时当作
HTTP 延迟或吞吐。

| 场景 | 同时持有的 scope | 存活请求堆峰值 MiB | 持有检查点 RSS 峰值 MiB |
| --- | ---: | ---: | ---: |
| 混合 8 输入 Transient | 64 | 0.74 | 5.55 |
| 4 个 lazy 输入并访问 | 64 | 0.82 | 5.62 |
| 4 参数异步 factory | 64 | 0.40 | 4.94 |
| 混合 8 输入 Scoped | 64 | 0.26 | 4.43 |
| 混合 8 输入 Transient | 512 | 5.51 | 11.98 |
| 每 scope 1 MiB 业务数据 | 128 | 128.41 | 135.40 |
| 每 scope 1 MiB 业务数据 | 256 | 256.73 | 272.88 |

21 个进程均通过限制核验及所有业务／析构断言。关闭 scope 后仍有调度容器的高水位
容量，不能描述成每波回到完全相同的堆大小；关闭 root 后存活请求堆约 32–34 KiB，
此时 Tokio runtime 仍存在。RSS 可能保留分配器页，不等于存活业务实例。

为复核高水位，又在相同 512 MiB／两核条件下各执行一次 512 波长循环：

| 场景 | 含预热的构造数／析构数 | 最后一次 scope 关闭后的 live B | 末尾连续不变波数 | root 关闭后的 live B |
| --- | ---: | ---: | ---: | ---: |
| Scoped，64 并发 | 32,960／32,960 | 128,205 | 255 | 33,157 |
| 1 MiB payload，256 并发 | 131,840／131,840 | 418,068 | 476 | 33,164 |
| 混合 Transient，512 并发 | 4,218,880／4,218,880 | 829,325 | 99 | 33,157 |

这些波数包含最后一次增长所在的检查点。混合场景在第 413 波（从 0 编号）仍增加
24 KiB，不能写成整个后半段完全不变。源码中的容器保留容量，以及固定 sysroot
HashMap 对删除标记的重排／扩容规则，与这种阶梯形高水位相符；不把每次变化武断归因
到某一张表。全部实例释放和末段平台支持这些有界负载下未观察到持续实例残留增长，
不能证明任意路径无泄漏或无限运行后绝无新高水位。

### 同机受限运行

两轮都使用上述数据库负载与限制，每个应用 scope 查询 8 次。第一轮同时持有
128 个 64 KiB payload；第二轮同时持有 256 个 1 MiB payload。下表为内核记录的
cgroup 峰值，子组峰值不必发生在同一时刻，不能相加替代父组峰值。

| 应用负载 | 父组整体峰值 MiB | 应用子组峰值 MiB | PostgreSQL 子组峰值 MiB | Redis 子组峰值 MiB |
| --- | ---: | ---: | ---: | ---: |
| 128 × 64 KiB | 797.71 | 18.00 | 640.00 | 140.10 |

两轮应用断言、pgbench 和 Redis 命令均成功，未记录 OOM、OOM kill 或 swap。

父组 `memory.events` 会累计子组事件，判断父组是否触顶应看 `memory.events.local`。

两轮 pgbench 分别完成 181,757／170,060 笔事务且无失败，Redis 合计分别执行

与分配器归还物理页是不同事件；部署预算必须容纳 RSS 高水位，不能只按 live 字节规划。
同时压力窗口平均使用约 91.4%／93.4% 的两核额度；CPU 已处于较高负载，不能由

### 部署判断与必须保留的边界

这些结果为 **2 GiB／两核、业务规模受控的小型服务** 提供受限资源下的可行性依据；
实际部署仍需用目标应用复测。框架本身在本轮负载下占用较小，业务同时持有的数据、
数据库和缓存决定主要预算。它们不能证明任意
应用只要启动成功就能长期稳定：本次是三个独立负载并行运行，没有实现 HTTP 服务、
真实业务 SQL、生产数据集、TLS、日志队列或完整监控。宿主 WSL2 也不是一台整机只有
2 GiB 的云 VM；系统、容器管理与额外服务必须实际落在预留预算内。

建议从以下边界启动部署，再用真实请求复测：

- 服务内存上限 512 MiB，两个 Tokio worker，入口限制并发及等待队列；数据库连接池
  先设 4–8。激活名额 32 只限制运行中的构造，不限制接受的请求或排队内存。
- 每个请求使用短生命周期 scope，并按协议关闭；避免通过长期 root 持续取得
  Transient。owner 的 journal 保留成功实例直到 owner 关闭，丢弃查询返回值不会
  自动结束这一生命周期，逃逸的强 lease 也可延长实例内存存活。
- PostgreSQL 可从本轮的 128MB shared_buffers、20 个最大连接与 2–4MB work_mem
  起步；work_mem 按执行操作分配，复杂查询和并行计划会叠加。effective_cache_size
  是优化器估计值，不是预分配内存，也不是数据库总内存上限。
- Redis 采用 128 MiB maxmemory 和明确淘汰策略，并预留进程及客户端开销。本轮只
  验证缓存模式；开启 RDB／AOF、复制或大量写入时，须另测 fork／写时复制与持久化峰值。
- 取消等待不会取消已接受的初始化；慢构造或异常清理应在业务侧有可观测的界限。
  root 会按既有契约汇总历史 scope 清理错误，持续出错不能视为稳定内存场景。

同轮较早的 Debug／current-thread 故障路径审查可作为补充：同一 root 三轮各积压
并取消 2000 个 scope，全部排空后的存活堆均为 1,810,390 B，累计 6000 个实例构造／
析构匹配；2000 个各含 4096 字符的清理错误则在 root 存活时累计约 8.34 MiB，直到
root 及聚合错误释放才回收。core 源码本轮未变，但这些数据不属于上面的 Release／
两核同机测量，也不应把契约性保留误写成已经修复的泄漏。

## 4. Core 紧凑存储与关闭工作空间：2026-10-02

本轮针对激活任务的小集合、关闭工作空间、长期表容量及每实例地址恢复器进行优化。
公开 API、执行计划 ABI、生命周期、取消后继续初始化、Lazy 接续、完整图关闭顺序
和强 lease 契约保持不变；core 没有增加运行期依赖。

### 实际改动与验证

- `Activation` 的普通查询和反向订阅使用零／单项内联存储，多项进入哈希集合；
  Lazy 发送端同样内联单项。Pending 子任务首次以内联槽位记录，第二项才分配
  完整槽位数组；展开时也不再创建逐任务目标 Vec。当前 x86_64 实测任务记录由
  **224 B 降至 136 B**，TaskState 仍为 56 B。大共享集合的表头另有一次 Box 分配，
  不能把单订阅路径收益推广成所有集合都少一次分配。
- 关闭排序复用协调器的下标数组、计数、堆和目标缓冲，直接置换原 journal；
  不再为每个 owner 建立全图实例桶和另一份结果容器。完整冻结 DAG 仍参与排序，
  含未实例化的中间节点；每轮关闭扫描只收集可推进 owner，复用其下标数组。
- 每 4096 个调度轮次依据整个窗口的元素峰值回收明显过剩容量，基准至少为 64 项，
  超过基准四倍才尝试缩至两倍；不按每次 scope 关闭缩容。静态图大小的关闭数组
  留待复用，随实例数增长的排序数组也参加窗口回收。无调度事件时不会定时唤醒，
  所以这里验证的是峰后低流量回收，不是完全空闲时限时归还内存。
- `TypedAddressResolver<T>` 改为类型关联常量静态提升后的只读引用，继续以准确
  类型检查从当前共享借用恢复地址。封装非零大小服务值时，`ErasedService::new`
  从 2 次分配降至 1 次；服务值为 ZST 时从 1 次降至 0。`ErasedService` 自身大小
  仍为 64 B。消除的是每实例
  一个 8 B 请求的独立 Box 及分配器开销，未缓存实例裸指针或移除 lease。

Core Debug／Release 各 146 项通过，严格 Clippy 通过；真实 CLI 的 DI fixture
30 项外层测试（含 68 个 UI 案例）、应用路径 workspace 387 项、11 个真实编译器
core 契约工程及 32 项跨 crate check/run/graph 全部通过。工作区另有 259 个既有
ignored doctest 未执行，不计入通过数。本轮没有 Windows 实机验收。
新关闭回归以独立传递可达性算法穷举全部 543 个四节点 DAG、长度 0～4 的全部
发布序列，共 185,163 案例，覆盖重复输入、重复实例、缺席中间节点和逆发布优先；
另验证真实 owner 复用工作空间不提前释放或额外保活实例。大共享订阅回归实际挂起
4096 个查询、交错取消 2048 个并保留 128 个 Lazy watch，检查正确退订和结果交付。

### 本轮基线与口径

before 是开始本轮优化时的 **622 文件完整工作区快照**，包含前述缺陷修复与用户原有
未提交修改；不使用 Git HEAD。after 从稳定后的生产源码另行冻结。两版使用相同
CLI／driver／bridge、固定 rustc 1.98.0、相同探针源码、21 个锁定 registry 依赖的
版本／来源／checksum。真实 sidecar 验证小图 9 节点、大图 1,033 节点，图内容一致；
大图增加 1024 个未激活 provider，每个 sparse scope 仍只创建 consumer 与 leaf。

Linux x86_64／WSL2，Release opt-level 3、16 codegen units、无 LTO；两个 Tokio
worker，进程 affinity 为 CPU 2、4。配对阶段没有设置 cgroup 内存或 CPU quota，
不能将 affinity 说成专用两核；后面的同机试验另行施加资源上限。正式采样期间
没有并行运行本任务的编译、其他基准或数据库压力。

九个场景 × before／after／manual 三版本 × 七轮，共 **189 个独立进程**，每轮
轮换版本顺序，另有 27 个功能烟测进程。正式计量合计 5,964,504 次业务查询，
包含预热的被跟踪实例共 4,227,216 次构造与同数析构；逐波和跨版本 checksum 一致。
Probe 不计共享根 Base／LazyBase，不能将这个计数称为全部 provider 的总构造数。

每进程三波预热，每 scope 查询八次；mixed512 同时持有 **4096 个**被跟踪
Transient，不能与第 3 节每 scope 十六次、8192 个实例的旧绝对值相除计算收益。
每波通过 barrier 同时持有全部实例，再放行并显式等待关闭。payload 每 scope
只有一个实际填充的 1 MiB 实例，八次查询复用它。

分配指标覆盖整波的请求任务、scope、业务查询、关闭及末尾 root.settle 检查；
启动与预热不计入每查询分配，但其常驻部分计入绝对 live／RSS。查询＋关闭段计时
排除了采样、settle、启动和预热，另保存完整进程 elapsed 与 user/system CPU。
计数 System allocator 的原子操作有开销，计时只代表带计数器的此项实验。
累计字节使用分配请求大小；存活堆不包括分配器头、碎片、栈、代码或文件缓存。

### 优化后与 PostgreSQL／Redis 同机复验

在配对测量结束后，使用同一个 after Release 二进制另做一次受限服务组验收：父组
**1536 MiB／两个 CPU 配额**，应用／PostgreSQL／Redis 子上限分别为
512／640／256 MiB，全部禁用 swap，CPU affinity 仍为 2、4；按 2 GiB 部署目标
为系统保留名义上的 512 MiB。该资源组包含数据库基准客户端，宿主系统及 daemon
仍在组外。

数据库与第 3 节配置相同：PostgreSQL 18.4，shared_buffers=128MB、max_connections=20、
work_mem=4MB、maintenance_work_mem=32MB，pgbench scale=10、8 客户端／2 线程；
Redis 8.6.3，50,000 个 key、每 value 1024 B，maxmemory=128MiB、allkeys-lru，
RDB／AOF 关闭，16 客户端、pipeline 4。数据库同时压力窗口为 60.278 秒；应用
运行三波预热加 700 波测量，每波同时持有 256 个 1 MiB payload、每 scope 查询
八次并持有 100 ms。

| 资源组 | 内核记录峰值 MiB | 限额 MiB |
| --- | ---: | ---: |
| 整个服务组 | **1109.070** | 1536 |
| 应用 | **378.559** | 512 |
| PostgreSQL | 640.016 | 640 |
| Redis | 93.070 | 256 |

子组峰值不同时发生，不能相加代替父组峰值；内核记账可在回收前略超子限额。
所有组 OOM、OOM kill 和 swap 均为零；父组 local.max=0，PostgreSQL local.max=215，
说明 PostgreSQL 发生过触限回收，并非没有内存压力。父组层级 events 中的 max
继承自 PostgreSQL。cgroup 还包含文件缓存与内核内存，不能直接当作业务存活堆。

pgbench 完成 143,561 笔事务，零失败；Redis GET 与 SET 各完成 400 万次，零 miss
与淘汰。应用完成 1,433,600 次计量查询；含预热的 payload 构造和析构均为 179,968。
关闭 root 后，计数的存活请求堆为 **24,286 B**，RSS 仍为 **275.785 MiB**，再次说明
释放实例与分配器归还物理页不是同一件事。部署预算必须容纳 RSS 高水位。
本次两个容器、专用数据库卷、scope、活动 cgroup 与临时 systemd 配置均已独立确认清理。

该结果继续提供 **2 GiB／两核同机部署规模受控的小型服务** 的可行性依据，入口并发与排队限制、
短生命周期 scope、数据库连接池和 Redis 容量预算仍然必要。本次是三个负载并行
运行的单次容量复验；不是业务 HTTP→SQL 端到端、真实 2 GiB 云主机、长时间稳定性
或 Redis 持久化／复制验收。它也不与第 3 节旧探针构成配对，不用两轮 RSS／TPS
差值宣称此次优化收益。

### 复现与证据

运行方式、manual 边界与计数窗口见 [Core 内存基准](../tools/bench-core-memory/README.md)。
`runner.py` 负责同源码构建、完整依赖／工具／二进制 hash 检查、轮换采样、分布及
配对区间；`colocated.py` 只运行已构建二进制，使用独立且带运行标签的临时资源。

本机证据保存在 `target/core-memory-20261002/`：

- `before.tar.gz`、`source-before.json`、`baseline/`、`after/`：实际工作区基线及实测源码。
- `build.json`、`bin/`、`toolchain/`：编译参数、固定工具、探针与生产源码哈希、保留二进制。
- `paired/samples.jsonl` 及逐进程 JSONL：189 个完整原始样本；`summary.json`、
  `SUMMARY.md` 和 `burst-recovery.json`：全部分布、配对区间、逐波恢复轨迹。
- `benchmark-review.md`、`paired-independent-review.md`：工件、口径、全部样本与
  精确重采样区间的独立复核。
- `colocated-after/`：实时 cgroup 样本、数据库／应用日志、限额、峰值、工作量和清理确认。
- `validation/`、`runtime-core-tests*.log`、`resolver/`：功能回归、分配负例、布局与安全审阅。
- `source-integrity.json`、`current-task.diff`：相对于本轮实际起点的最终保护核对与变更。

这些 `target/` 文件是本机审阅证据，不随仓库分发；正式说明和可复用脚本保留在
本报告与 `tools/bench-core-memory/`。历史各节仍只代表各自原始快照，不相加为总收益。
